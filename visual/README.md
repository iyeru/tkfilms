# ビジュアル回帰チェック

`design/`（原本）と `src/`（React版）を同じセクション・同じビューポートでスクリーンショットして比較する仕組み。
React版が原本から見た目でズレていないかを、目視ではなく機械的に確認するためのもの。

## 使い方

```bash
npm install

# 1. design/ を基準にベースライン画像を作る（design/ を直接編集した時だけ再実行）
npm run visual:baseline

# 2. src/ を基準に比較する（セクションを1つ変換するたびに実行する）
npm run visual:test

# 差分があれば HTML レポートで確認できる
npm run visual:report
```

## 合格条件

公開を `design/` から `src/` に切り替えてよい、と判断するための条件。

- **`npm run visual:test` が全件通過する**（現在27件）。通過の基準は `playwright.config.ts` の
  `maxDiffPixelRatio: 0.02`、つまり画素の2%まで違ってよい。
- **skip されているテストが、下の「意図した乖離」に挙げたものだけ**である。
  未実装（`reactSelector` が `null`）による skip が1件も残っていない。
- **`failed` がゼロ。** 落ちたテストは自動で1回だけやり直される（`retries: 1`）。
  やり直しで通れば `flaky`＝サムネイルの取得に失敗しただけで、見た目のズレではない。
  2回とも落ちた `failed` だけが本当のズレなので、そこだけ見ればいい。
- **ベースラインが最新の `design/` から、比較と同じ環境で撮られている。**
  `design/` を書き出し直したら `npm run visual:baseline` からやり直す。
- **About は機械で見ていない**（下記）ので、切り替え前に3幅とも目視で確認する。

### 意図した乖離（原本に合わせ直さないもの）

ここに挙げた以外の差分は「直すべきズレ」として扱う。乖離を足したときは必ずここにも書く。

| 箇所 | 何が違うか | 扱い |
| --- | --- | --- |
| About | `src/` の本文を提案資料の自己紹介に差し替え、実績の箇条書きも足した（#24）。原本は仮テキストのままで、高さも中身も別物になっている | 比較対象から外す（`sections.ts` の `diverged`）。3幅ぶん skip される |
| Hero の肩書き | 同じく #24 で `Filmmaker & Cinematographer` → `Marketer & Filmmaker` に変更 | 比較は続ける。文字数が近く差分が閾値に収まるので通るが、**この1行は検証されていない** |
| 動画（iframe） | 再生位置が撮る度に変わり、原理的に固定できない | 撮影中だけ `visibility: hidden`。枠の位置と大きさは比較される |
| works のカルーセル背景 | 原本のプレビュー機能が実写真を自動で差し込む | 斜線のプレースホルダーに固定して撮る |
| フィルムグレイン | ランダムノイズなので比べても意味がない | 撮影中だけ非表示 |

`design/` は書き出し直すと手を入れた分が消える生成物なので、**原本側を書き換えて乖離を埋めにいかない。**
`src/` が原本より先に進んだ箇所は、原本に戻すのではなく乖離として記録する。

## 仕組み

- `visual/sections.ts` にセクション一覧と、design側/react側それぞれのセレクタを定義している。
  `reactSelector` が `null` のセクションはまだ `src/` に実装がないという意味で、自動的にテストが skip される。
  セクションを作ったらここを埋める。`diverged` に理由を書いた場合も skip されるが、意味は逆で
  「原本に合わせ直すつもりが無い」という宣言（上記「意図した乖離」）。
  id ではなくセレクタで持っているのは、原本が id を振っているのが home/works/about/contact の4つだけで、
  Equipment・Gram・Footer には無いため（原本に id を足しても書き出し直しで消えるので当てにできない）。
- `visual/hover-targets.ts` に、design/ で `style-hover` が定義されている要素のうち `src/` に実装済みの
  ものを一覧化している。`compare.spec.ts` の `hover` ブロックが各要素を `hover()` してからスクリーンショット
  を撮る（下記「ホバー状態の比較」参照）。`reactSelector` が `null` なら未実装として自動skip。
- `playwright.config.ts` が `design/` を静的配信するサーバ（4174番）と `npm run dev`（5175番）を両方起動し、
  同じスナップショットファイル名（`{arg}.png`、プロジェクト名を含まない）を両方のプロジェクトで共有する。
  そのため `design` プロジェクトで撮った画像がそのまま `react` プロジェクトの比較対象になる。
- ローディング演出や scroll-reveal のタイミング差でテストが揺れないよう、
  `reducedMotion: 'reduce'` の指定とCSSトランジション無効化、固定待機を入れている（`compare.spec.ts` 参照）。

### 撮り方

- **セクションは高さぶん丸ごと撮る。** `fullPage` で撮ってからドキュメント座標で切り出しているため、
  画面より高いセクション（works は desktop で 2603px）も頭から終わりまで比較対象になる。
  撮影前に必ずスクロール位置を先頭へ戻す。ヘッダーがスクロール量で高さと背景を変える
  （75px透明 ⇔ 55px塗り）ので、位置が揃っていないと同じ画にならない。
- **撮る前にページ全体を一度なめる。** 画面外の要素を描画させ、サムネイルを読み込ませるため。
- **幅は3本。** `mobile(390)` / `tablet(900)` / `desktop(1440)`。折り返しは `duo(760px)` と
  `wide(1200px)` の2本だけ（`src/index.css`）なので、両方の下・両方の上・その間、で3本になる。
  tablet の帯は Works が2カラムに割れる一方でヘッダーはハンバーガーのまま、サイドドットも出ない
  組み合わせで、ここでしか通らない。
- **`state` ブロック**はセクション単位では通らない状態を撮る。今はドロワーを開いた状態だけ
  （本文が左へ寄る・暗幕が乗る・パネルが出るの3つが同時に起きる）。開閉ボタンは 1200px 未満でしか
  出ないため desktop は対象外。

## ホバー状態の比較

通常のテスト（`section.key`）は撮影を安定させるため `transition: none !important; animation: none !important;`
で全アニメーションを無効化しており、`:hover` 状態も再現していない。そのため、ボタンの色反転や
カードのホバーオーバーレイなど `style-hover` に由来する見た目の差分はここでは検知できない。

これを補うのが `hover` ブロック（`hover-<key>.png` というスナップショット名）。
トランジションを無効化した状態でも `locator.hover()` は問題なく使え、無効化済みなのでホバー後の
最終スタイルへ即座に切り替わる（アニメーション待ちが不要で、通常のテストと同じ安定性で撮れる）。
対象要素は `visual/hover-targets.ts` に追加していく。

- ホバーで `scale()` する要素があるため、`boundingBox()` の周囲に余白（`pad`）を持たせてクリップしている。
- ホバーはポインタ操作前提のため、デスクトップ幅のみで比較する（モバイルはホバー自体が対象外）。

## 運用の勘所

- セクション単位で変換 → `npm run visual:test` → 該当セクションだけ差分を見る、のサイクルで進める。
  1回で全セクションをまとめて変換しない。
- **閾値（`maxDiffPixelRatio: 0.02`）は緩めない。** 通らない差分が出たら、まず原因を突き止める。
  原本に合わせ直さないと決めた箇所は、閾値をいじるのではなく「意図した乖離」に記録して外す。
- ベースライン画像（`visual/__screenshots__/`）はコミットする。design/ を直接触らない限り再生成は不要。
- フォントレンダリングはOS依存なので、ベースライン生成と比較は同じ環境（同じマシン、または同じCI）で行うこと。

## 動作確認で分かったこと（ハマりどころ）

- **`page.addStyleTag()` は `page.goto()` より後に呼ぶ。** 先に呼ぶと直後のナビゲーションで
  注入したスタイルごと消え、何も効かなくなる（`compare.spec.ts` の `injectFreezeStyles` 参照）。
- **design/ の home・featured・works セクションには実際に YouTube 埋め込みが自動再生されている。**
  `[ main film — 16:9 embed ]` のような角括弧表記は静止テキストに見えるが、実際のレンダリングでは
  検索でヒットした本物の動画が iframe で流れる。動画フレームは撮影の度に変わるため
  スクリーンショットが絶対に安定しない。`compare.spec.ts` で `iframe { visibility: hidden }` にして回避している。
- **works の「THE LONG LIGHT」カルーセルバナーも同様に実写真が自動で差し込まれる**（design/ の
  プレビュー機能によるもので、静的なHTMLソースには現れない）。背景だけ斜線に固定して隠している。
  他のセクションでも同種の「実は動いている」要素が見つかったら、同じやり方で追加していく。
- インラインstyleを属性セレクタで狙うときは、ブラウザが実際にDOMへ反映した後の表記
  （`opacity:.055` ではなく `opacity: 0.055`、`aspect-ratio:21/9` ではなく `aspect-ratio: 21 / 9` など、
  コロン後・スラッシュ前後にスペースが入る）に合わせること。静的HTMLソースの表記のままだとマッチしない。
- カルーセルのように「不安定な要素を隠す」場合、`visibility: hidden` で丸ごと隠すと中の子要素（ボタン等）も
  操作できなくなる。ホバーテストのようにインタラクションが必要な場合は、不安定な部分（背景写真など）だけを
  固定値で上書きする方が良い（`compare.spec.ts` のカルーセル背景のルール参照）。
- 同じ `class`（例: `.hatch` のような自作ユーティリティ）を複数の別要素に使い回していると、
  `.first()` で狙った要素と違うものにヒットすることがある。ホバー対象のセレクタは
  「その要素にしか付かない」クラスの組み合わせまで絞り込むこと。
- **写真の食い違いに見える差分は、たいてい読み込み待ちの失敗。** 原本は写真を書き出し時に
  取り込んで `blob:` で持っているので待たずに出るが、React版は `i.ytimg.com` から都度取ってくる
  （`src/content.ts` の `frame()`）。間に合わないと枠が真っ黒のまま撮れて、
  「写真が全部違う」ような巨大な差分になる。実際には同じ動画の同じサムネイルで、撮り直すと通る。
  `compare.spec.ts` の `waitForPhotos()` で読み込みを待ち、読めなかった URL はエラーにしている
  （黙って真っ黒を撮ってデザイン崩れと区別が付かなくなるのを避けるため）。
- **画面幅で入れ替わる値を、要素を特定する目印に使わない。** works のカルーセルバナーは
  `duo` 未満で `4/3`、以上で `21/9` になるので、比率で引くと片方の幅でしか当たらない。
  「前へ／次へボタンを直下に持つ枠」のような、幅に依らない位置関係で引くこと。
- **クリップ範囲は整数に丸めてから渡す。** `getBoundingClientRect()` は小数を返すので、
  ページの別の場所（About の本文量など）が変わって要素の小数座標がずれるだけで、
  切り出される画像の高さが 1px 動くことがある。大きさが 1px でも違えば比較は問答無用で失敗し、
  中身は同じなのに「フッターが崩れた」ように見える。`compare.spec.ts` の `documentBox()` で丸めている。
