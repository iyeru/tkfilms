# ビジュアル回帰チェック

`src/`（このサイト）を7セクション×3幅でスクリーンショットして、**前回撮った自分自身と比べる**仕組み。
見た目を意図せず壊していないかを、目視ではなく機械的に確認するためのもの。

## 経緯

もとは `design/`（デザイン原本）と `src/`（React版）を突き合わせて、
「React への移植がズレていないか」を見るための道具だった。移植は #26 で完了し、
配信も `src/` のビルド結果に切り替わっている。

その後のデザイン見直しは**意図的に原本から離れる変更**ばかりで、原本と比べ続けると
「意図した乖離」の除外リストが増える一方になり、比較の網が穴だらけになる。
そこで原本追従をやめ、**ベースラインを `src/` 自身で撮り直して回帰テストに用途変更した。**

`design/` は残してあるが、もう配信もテストもしていない。見た目の由来を辿るための資料。

## 使い方

> ⚠️ **実行前に必ず shinta に断りを入れる。1回およそ3分かかる。**
> 30件それぞれでページを読み込み直し、3秒待ち、全画面をスクロールし、画像の読み込みを
> 待ってから撮っているため。詳しくは [CLAUDE.md](../CLAUDE.md)。
> テスト名で絞るなら `npx playwright test -g "about"`。

```bash
npm install

# 見た目を変えていないはずの変更で、壊れていないか見る
npm run visual:test

# 差分があれば HTML レポートで確認できる
npm run visual:report

# 差分が「意図した変更」だと確認できたら、ベースラインを撮り直す
npm run visual:baseline
```

### ベースラインを撮り直すのは「差分を確認した後」

`visual:baseline` は全スナップショットを今の見た目で上書きする。**先に `visual:test` を回して
レポートで差分を見て、それが意図した変更だと確認してから**撮り直す。
確認せずに撮り直すと、壊れた見た目がそのまま新しい正解になる。

撮り直したら、その PR にスナップショットの差分も含める。
「何をどう変えたか」がレビューで画像として見えるのが、この運用の一番の利点。

## 見ているもの

- **セクション7つ × 幅3本 = 21件。** Hero / Works / About / Equipment / Contact / Gram / Footer
- **ホバー状態7件**（デスクトップ幅のみ）
- **ドロワーを開いた状態2件**（mobile / tablet）

合計30件。合否の基準は `playwright.config.ts` の `maxDiffPixelRatio: 0.02`、つまり画素の2%まで違ってよい。

**閾値は緩めない。** 通らない差分が出たら、まず原因を突き止める。
意図した変更なら閾値をいじるのではなくベースラインを撮り直す。

落ちたテストは自動で1回だけやり直される（`retries: 1`）。
やり直しで通れば `flaky`＝サムネイルの取得に失敗しただけで、見た目のズレではない。
2回とも落ちた `failed` だけが本当のズレなので、そこだけ見ればいい。

### 撮影中だけ隠しているもの

どちらも「毎回変わって絶対に安定しない」もので、隠さないとテストが成立しない。

| 隠すもの | 理由 |
| --- | --- |
| `iframe`（YouTube 埋め込み） | 再生位置が撮る度に変わる。`visibility: hidden` なので枠の位置と大きさは比較される |
| `video`（home の背景動画） | 同じく再生位置が毎回変わる。加えて Playwright の Chromium は H.264 を再生できず真っ黒に描くので、隠して背景の `poster` を比較している |
| `.film-grain` | 全画面に敷く粒。残すとどのピクセルも少し違う状態になり、本当の差分がノイズに埋もれる |

## セクションを増減・並べ替えるとセレクタが壊れる

`visual/sections.ts` は id ではなく構造や見出し文字列でセレクタを引いている箇所がある。
id を持っているのは `home` / `works` / `about` / `contact` の4つだけで、
Equipment・Gram・Footer には無い（`design/` 原本から引き継いだ構成）。

| セクション | セレクタ | 壊れる操作 |
| --- | --- | --- |
| Equipment | `section:has(h2:text-is("Equipment"))` | 見出し文字列の変更・セクション削除 |
| Gram | `#contact + section` | Contact との前後入れ替え・セクション削除 |

セクション構成を変えるタスクでは、`sections.ts` の追従も作業に含める。
`src/` は自分で書いているので id を足してもよい（原本と違い、書き出し直しで消えない）。

### セクションを足すと、その下のセクションの撮影がずれることがある

`fullPage` で撮ってからドキュメント座標で切り出しているため、**上に何かを挟むと下の
セクションの切り出し位置がずれる**ことがある。中身は同じなのに縦に数pxずれた画が撮れ、
差分としては「全部違う」ように見える。

実例: Works と About の間に Clients セクションを足したところ、`about-desktop` だけが
縦 8px ずれて必ず落ちる状態になった（ずらして重ねると差分ピクセルは0）。
`#about` の座標自体はページ側で測ると完全に安定しており、撮影側の問題。

セクションを足す PR でこれが出たら、**ページが壊れたのではなく撮影がずれている**方を先に疑う。
`documentBox()` と `toHaveScreenshot({ fullPage: true, clip })` の組み合わせが原因。

## 仕組み

- `visual/sections.ts` にセクション一覧とセレクタ、`visual/hover-targets.ts` にホバー対象を定義している。
  対象を増やすならこの2ファイルに足して `visual:baseline` を回す。
- `playwright.config.ts` が `npm run dev`（5175番）を起動し、`visual/regression.spec.ts` が撮る。
- ローディング演出や scroll-reveal のタイミング差でテストが揺れないよう、
  `reducedMotion: 'reduce'` の指定とCSSトランジション無効化、固定待機を入れている。

### 撮り方

- **セクションは高さぶん丸ごと撮る。** `fullPage` で撮ってからドキュメント座標で切り出しているため、
  画面より高いセクション（works は desktop で 2603px）も頭から終わりまで比較対象になる。
  撮影前に必ずスクロール位置を先頭へ戻す。ヘッダーがスクロール量で高さと背景を変える
  （75px透明 ⇔ 55px塗り）ので、位置が揃っていないと同じ画にならない。
- **撮る前にページ全体を一度なめる。** 画面外の要素を描画させ、サムネイルを読み込ませるため。
- **幅は3本。** `mobile(390)` / `tablet(900)` / `desktop(1440)`。折り返しは `duo(760px)` と
  `wide(1200px)` の2本だけ（`src/index.css`）なので、両方の下・両方の上・その間、で3本になる。
  tablet の帯は Works が2カラムに割れる一方でヘッダーはハンバーガーのまま、サイドドットも出ない
  組み合わせで、ここでしか通らない。
- **`state` ブロック**はセクション単位では通らない状態を撮る。今はドロワーを開いた状態だけ
  （本文が左へ寄る・暗幕が乗る・パネルが出るの3つが同時に起きる）。開閉ボタンは 1200px 未満でしか
  出ないため desktop は対象外。

### ホバー状態

通常のテスト（`section.key`）は撮影を安定させるため `transition: none !important; animation: none !important;`
で全アニメーションを無効化しており、`:hover` 状態も再現していない。そのため、ボタンの色反転や
カードのホバーオーバーレイなどの差分はここでは検知できない。

これを補うのが `hover` ブロック（`hover-<key>.png` というスナップショット名）。
トランジションを無効化した状態でも `locator.hover()` は問題なく使え、無効化済みなのでホバー後の
最終スタイルへ即座に切り替わる（アニメーション待ちが不要で、通常のテストと同じ安定性で撮れる）。
対象要素は `visual/hover-targets.ts` に追加していく。

- ホバーで `scale()` する要素があるため、`boundingBox()` の周囲に余白（`pad`）を持たせてクリップしている。
- ホバーはポインタ操作前提のため、デスクトップ幅のみで比較する（モバイルはホバー自体が対象外）。

## この比較で見えていないもの

**日本語の字形と行の折り返し。** 撮影に使っている環境（WSL2）に日本語フォントが入っておらず、
スクリーンショットの日本語はすべて豆腐（□）になる。`fc-list :lang=ja` が空なら未インストール。

ベースラインも比較も同じ豆腐で描かれるため、**回帰の検出そのものは成立している。**
ただし豆腐と実際の日本語では文字幅が違うため、実物のブラウザとは行の折り返し位置がズレている。
つまり「前回から変わっていないか」は見えているが、「実物で崩れていないか」までは見えていない。

`sudo apt install fonts-noto-cjk` を入れれば実物に近い比較になる。入れた場合は
文字の描かれ方が全部変わるので、`npm run visual:baseline` から撮り直すこと。

**フォントレンダリングはOS依存なので、ベースライン生成と比較は同じ環境（同じマシン、または同じCI）で行う。**

## 動作確認で分かったこと（ハマりどころ）

- **`page.addStyleTag()` は `page.goto()` より後に呼ぶ。** 先に呼ぶと直後のナビゲーションで
  注入したスタイルごと消え、何も効かなくなる（`regression.spec.ts` の `injectFreezeStyles` 参照）。
- **home の背景動画（`public/media/hero.mp4`）は、テスト用のブラウザでは絵が出ない。**
  Playwright が持つ Chromium は H.264 を含まないビルドで、`readyState` は 4 まで進むのに
  描かれるのは真っ黒になる（canvas に写しても同じ）。実物のブラウザでは再生される。
  `video { visibility: hidden }` で隠し、Hero セクションの背景に敷いてある `poster`
  （`public/images/hero-poster.jpg`）の方を比較している。
- **home・works には実際に YouTube 埋め込みが自動再生されている。**
  `iframe { visibility: hidden }` で隠しているが、通信自体は続いていて再描画が止まらず、
  `toHaveScreenshot` の安定待ちがタイムアウトすることがある。`blockEmbeds()` で通信ごと遮断している。
- **写真の食い違いに見える差分は、たいてい読み込み待ちの失敗。** サムネイルは `i.ytimg.com` から
  都度取ってくる（`src/content.ts` の `frame()`）。間に合わないと枠が真っ黒のまま撮れて、
  「写真が全部違う」ような巨大な差分になる。`waitForPhotos()` で読み込みを待ち、
  読めなかった URL はエラーにしている（黙って真っ黒を撮ってデザイン崩れと区別が付かなくなるのを避けるため）。
- **画面幅で入れ替わる値を、要素を特定する目印に使わない。** works のカルーセルバナーは
  `duo` 未満で `4/3`、以上で `21/9` になるので、比率で引くと片方の幅でしか当たらない。
  「前へ／次へボタンを直下に持つ枠」のような、幅に依らない位置関係で引くこと。
- **クリップ範囲は整数に丸めてから渡す。** `getBoundingClientRect()` は小数を返すので、
  ページの別の場所（About の本文量など）が変わって要素の小数座標がずれるだけで、
  切り出される画像の高さが 1px 動くことがある。大きさが 1px でも違えば比較は問答無用で失敗し、
  中身は同じなのに「フッターが崩れた」ように見える。`regression.spec.ts` の `documentBox()` で丸めている。
- 同じ `class`（例: `.hatch` のような自作ユーティリティ）を複数の別要素に使い回していると、
  `.first()` で狙った要素と違うものにヒットすることがある。ホバー対象のセレクタは
  「その要素にしか付かない」クラスの組み合わせまで絞り込むこと。
